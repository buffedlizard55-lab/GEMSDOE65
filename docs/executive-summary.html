Step 3 — the error this repo engineers out permanently

"Predicted values must be in range [0, 1]" — two mechanisms, both measured here:

  • M1 — float32 sentinel inside the footprint. training_features.tif declares nodata as -3.4028234663852886e+38 (the float32 minimum, not NaN). Measured: 0 sentinel band-pixels across the 19 bands lie inside the 5,167,373-pixel scoring footprint (max 0 in one band). A pipeline that does not replace them ships −3.4e38.
  • M2 — footprint mask mismatch. A footprint taken from a feature band is smaller than the template's, which strands scored pixels as NaN. NaN fails any ((v>=0)&(v<=1)).all() check.

Both are handled by construction in src/gems65/submission.py: the footprint is read from the pinned sample_submission.tif, every in-footprint output pixel is a finite float32 in [0,1], and scripts/validate_submission.py re-reads the written file and refuses to pass it otherwise.

Step 4 — how the score is computed (so the file can be reasoned about)

k(d) = max(1 - d/R, 0),  R = 300 m = 3 px at 100 m
TP_w = sum over truth pixels g of  max over x with d(x,g) <= R  of  p(x) k(d(x,g))
FP_w = sum over x with p(x) > 0   of  p(x) [1 - max over g of k(d(x,g))]
FN_w = sum over g                 of  [1 - max over x of p(x) k(d(x,g))]  =  |G| - TP_w
DTI  = TP_w / (TP_w + 0.2 FP_w + 0.8 FN_w)

Two exact consequences, both brute-force verified in tests/test_metric.py:

  • DTI = T / (0.2 (T + S − M) + 0.8 K) with S = emitted mass, M = mass-weighted kernel coverage, K = |G|. For a dot field, DTI = T / (0.2 N + 0.8 K).
  • Adding one unit of mass raises DTI iff its realised kernel credit k > 0.2 · DTI (≈0.056 at 0.28). The denominator rises by exactly 0.2 wherever the mass lands.
  • Known USGS/INGENIOUS fault pixels are masked out of scoring (DrivenData staff, forum thread 11516), so mass placed on them earns neither TP nor FP. This emitter places zero mass there.
